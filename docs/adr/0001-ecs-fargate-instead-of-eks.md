# ADR 0001: ECS Fargate (not EKS) for the referrals API

**Status:** accepted · **Date:** 2026-11

## Context
The workload is a small set of stateless HTTP services plus a relational
database. The team that runs it is small and also supports product, data and AI
teams. The infrastructure must be reliable and cheap to operate more than it
must be flexible.

## Decision
Run containers on **ECS with Fargate**. Manage everything with Terraform.

## Why
| | ECS Fargate | EKS |
|---|---|---|
| Control plane cost | none | ~$73/month per cluster |
| Things to patch and upgrade | task definitions only | cluster version every ~14 months, node AMIs, add-ons (CNI, CoreDNS, kube-proxy) |
| IAM per workload | task role, native | IRSA / Pod Identity setup |
| Deployment safety | rolling update + circuit breaker with automatic rollback, built in | needs Argo Rollouts / Flagger for the same |
| Ecosystem (Helm charts, operators, CRDs) | small | large |
| Portability | AWS only | any Kubernetes |

For this workload the EKS advantages (operators, CRDs, multi-cloud portability)
are not needed, and its costs (upgrades, add-ons, cluster-level security) are
real. ECS gives the deployment safety we need with less to operate.

## Consequences
- No ArgoCD (it deploys to Kubernetes only). GitOps-style delivery is done with
  Terraform + GitHub Actions: see ADR 0003.
- No Helm. Task definitions are generated by one reusable Terraform module
  (`modules/ecs-service`) used by the API, the migration task and the four
  observability services.
- If the platform grows to many teams that want self-service and Kubernetes
  tooling, revisit: EKS with ArgoCD and the same Terraform modules for
  networking and RDS.
